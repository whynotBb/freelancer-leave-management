# 프리랜서 휴가 관리 시스템 설계 문서

- 작성일: 2026-08-24
- 상태: 승인 대기 (사용자 리뷰 전)

## 1. 배경 및 목적

프로젝트에 투입된 프리랜서 인력을 대상으로 연차 발생·소멸, 휴가계 제출, 결재, 현황 대시보드를
제공하는 휴가 관리 웹 애플리케이션을 신규로 구축한다. 정규 사원용 시스템이 아니라 외부 인원인
프리랜서를 대상으로 하므로, 계정 생성·승인 절차와 결재 구조를 최대한 단순하게 유지한다.

## 2. 범위

**포함**
- 프리랜서 자율 회원가입 + 관리자 승인 로그인
- 월 단위 연차 자동 발생 및 입사 1년 시점 잔여연차 소멸
- 연차(전일) / 반차(오전·오후) 휴가계 작성·제출
- 단일 결재자 방식의 승인/반려 워크플로
- 개인 대시보드(내 휴가 현황 / 내 결재 현황)
- 관리자 전용 기능: 가입 승인, 프리랜서 정보 관리, 연차 수동 조정, 공휴일 관리
- 접속 중 한정 실시간 알림(관리자: 가입 대기·결재 대기 발생 / 프리랜서 본인: 결재 완료) — 상세는
  7.1절 참조

**제외 (추후 확장 가능)**
- 다단계 결재라인
- 휴가계 예약 제출(이미지 참고자료에 있었으나 요구사항에는 없음)
- 시간 단위 정밀 반차 계산 (분 단위 등)
- 캘린더 공유 기능
- 접속하지 않은 사용자 대상 알림(이메일, 브라우저 푸시 등)
- 프리랜서 휴가 이력 등 엑셀 일괄 추출 (요청됨, 세부 요구사항 미확정 — 추후 별도 설계)
- 사이트 사용 히스토리(접속/행동 로그) 표출 (요청됨, 세부 요구사항 미확정 — 추후 별도 설계)

## 3. 사용자 역할

| 역할 | 설명 |
|---|---|
| 관리자(HR) | 가입 승인/거절, 프리랜서 정보(입사일·직급·부서·기본 결재자) 관리, 연차 수동 조정, 공휴일 관리, 시스템 전반 관리 |
| 프리랜서 | 휴가계 작성/제출/조회. 타 프리랜서의 결재자로 지정될 수 있음(별도 역할 플래그 없이 결재자 필드에 지정되는 방식) |

관리자 본인도 결재자로 지정될 수 있다.

> 9장의 관리자 메뉴(결재담당자 관리 추가)도 함께 갱신되었으니 최신 내용은 해당 문서를 따른다.

## 4. 인증 & 계정 승인 플로우

1. 프리랜서가 이메일/비밀번호로 회원가입을 신청한다.
2. 계정 상태는 `대기`로 생성되며, 이 상태에서는 로그인이 차단된다.
3. 관리자가 관리자 화면에서 가입 신청을 확인하고 `승인` 또는 `거절` 처리한다.
   - 승인 시 프리랜서의 입사일·직급·부서·기본 결재자를 함께 지정한다(승인 시점 또는 승인 후 편집).
   - 거절 시 로그인이 계속 차단된다.
4. 승인된 계정만 이메일/비밀번호로 로그인 가능하다.

인증은 자체 이메일/비밀번호 방식으로 구현하며(소셜 로그인 없음), 세션 관리 방식은 구현 단계에서
프레임워크에 맞춰 확정한다.

## 5. 연차 데이터 모델

### 5.1 엔티티

- **User**: id, 이름, 이메일, 비밀번호 해시, 역할(관리자/프리랜서), 가입승인상태(대기/승인/거절),
  입사일, 직급, 부서/프로젝트, 기본 결재자ID
- **LeaveGrant** (연차 발생 원장): id, userId, 발생일, 수량(고정 1일), 만료일(입사일 기준 1년 후),
  소멸여부
- **LeaveRequest** (휴가계): id, userId, 결재자ID, 제목, 시작일, 종료일,
  유형(연차/오전반차/오후반차), 신청일수(0.5 단위), 사유, 상태(임시저장/대기/승인/반려/취소),
  제출일시, 처리일시
- **Holiday** (공휴일 테이블): 날짜, 명칭
- **Notification** (실시간 알림): id, 수신자userId, 유형(가입대기/휴가제출/휴가승인/휴가반려),
  참조ID(userId 또는 leaveRequestId), 메시지, 읽음여부, 생성일시 — 상세는 7.1절 참조

연차를 단순 숫자 카운터가 아닌 **원장(배치) 방식**으로 관리함으로써, 발생/사용 이력 추적과
대시보드 집계("발생 n / 사용 n / 미사용 n"), 관리자의 수동 조정(가감 이력 포함)을 자연스럽게
지원한다.

### 5.2 연차 발생 로직

- 매일 또는 매월 1일 배치로, 각 프리랜서의 입사일 기준 만근 여부를 판정한다.
- **만근 판정**: 평가 대상 월에 **승인된 연차(전일) 사용 일수가 없으면** 만근으로 인정한다.
  - 반차(오전/오후) 사용은 만근 판정에 영향을 주지 않는다. 즉 반차만 사용한 달에도 정상적으로
    연차가 발생한다.
- 만근이 인정되면 `LeaveGrant` 1건(수량 1일)을 생성한다.

> **갱신 안내(2026-08-26):** 이 절의 만근 판정 규칙("승인된 연차 사용이 있으면 만근 아님")은
> 실제 정책과 달랐던 것으로 확인되어
> `docs/superpowers/specs/2026-08-26-attendance-based-leave-grant-design.md`의 3장에서 정정되었다.
> 정정된 규칙: 연차 사용은 만근 판정에 영향을 주지 않으며, 관리자가 수동으로 지정한 "만근 예외"만
> 그 달의 연차 발생을 막는다. 자동 발생 배치(Cron) 구현도 해당 문서 5장에서 함께 다룬다. 최신
> 내용은 그 문서를 따른다.

### 5.3 연차 소멸(이월/초기화) 로직

- 입사일 기준 12개월(1년)이 되는 시점에, 그동안 쌓인 미사용 `LeaveGrant` 잔여분을 일괄 소멸
  처리한다.
- 13개월차부터는 동일한 월 단위 발생 로직이 새 사이클로 반복되며, 매 입사기념일(1년 단위)마다
  동일하게 리셋된다.

### 5.4 잔여연차 계산

```
잔여연차 = 소멸되지 않은 LeaveGrant 합계 − 승인된 LeaveRequest 사용량 합계
```

## 6. 휴가계 작성 & 제출

**입력 항목**
- 결재자 지정 (기본값: 프로필의 기본 결재자, 신청 시 변경 가능)
- 제목
- 신청인 / 직급 / 부서 (자동 표시, 읽기 전용)
- 시작일 ~ 종료일 (datepicker)
- 휴가 유형: 연차(전일) / 오전반차 / 오후반차
- 신청일수 (자동 계산, 읽기 전용)
- 잔여연차 (자동 표시, 읽기 전용)
- 사유

**신청일수 계산 규칙**
- 주말, `Holiday` 테이블에 등록된 공휴일은 신청일수에서 제외한다.
- 반차는 0.5일로 계산하며, 오전/오후 구분은 표시 목적으로만 사용하고 시간 단위 정밀 계산은
  하지 않는다.
- 공휴일 데이터가 없는 기간은 주말만 제외하고 계산하며, 관리자가 추후 공휴일을 등록하면 이후
  계산부터 반영된다(과거 확정 문서는 재계산하지 않음).

**액션**: 임시저장, 제출. (참고 이미지의 "예약" 기능은 이번 범위에서 제외)

**유효성 검증**
- 신청일수가 잔여연차를 초과하면 제출을 차단한다.
- 결재자가 지정되지 않으면 제출을 차단한다.
- 동일 기간에 이미 대기/승인 상태인 본인 문서가 있으면 경고를 표시하되 제출은 차단하지 않는다.

## 7. 결재 워크플로

**상태 전이**: `임시저장` → `제출(대기)` → `승인` / `반려`

- 신청인은 `대기` 상태에서만 직접 취소할 수 있다.
- `승인` 이후 취소는 관리자만 처리할 수 있다(관리자 전용 기능).
- 반려 시 결재자는 반려 사유를 입력한다.
- 승인 처리 시점에 `LeaveRequest` 상태가 확정되고, 이후 잔여연차 계산에 사용량으로 반영된다.

**알림**: 대시보드 진입 시 쿼리 기반으로 "결재 대기 문서 n건" 메시지를 표시하는 것과 별개로,
접속 중에는 7.1절의 실시간 알림도 함께 동작한다.

## 7.1 실시간 알림

접속 중인 사용자에게만 제공되는 실시간 알림이다. 오프라인 상태의 사용자에게 별도로 발송되는
알림(이메일, 브라우저 푸시 등)은 이번 범위에 포함하지 않는다.

**알림 대상 및 트리거**

| 대상 | 트리거 |
|---|---|
| 관리자 | 신규 가입 신청(계정 상태가 `대기`로 생성) 발생 시 |
| 관리자 | 휴가계가 `제출(대기)` 상태로 전환될 때 |
| 프리랜서(신청인 본인) | 본인 휴가계가 `승인` 또는 `반려`로 처리될 때 |

**구현 방식**
- 위 이벤트가 발생하는 시점(가입 신청 API, 휴가계 제출 API, 승인/반려 API 내부)에 전용
  `Notification` 레코드를 생성한다. `User`/`LeaveRequest` 원본 테이블을 클라이언트가 직접
  구독하지 않고, 이 전용 테이블만 구독 대상으로 삼는다 — 원본 테이블을 직접 노출하면 권한
  범위를 넘어선 데이터가 실시간 이벤트에 포함될 위험이 있기 때문이다.
- 클라이언트는 본인에게 해당하는 `Notification`만 실시간 구독한다: 관리자는 `유형`이
  가입대기/휴가제출인 전체 레코드를, 프리랜서는 본인이 `수신자userId`인 레코드만 구독한다.
- DB는 Supabase(Postgres, 10장 참조)를 사용하며, Supabase Realtime의 Postgres Changes 기능으로
  `Notification` 테이블의 INSERT 이벤트를 구독해 실시간으로 반영한다.

## 8. 대시보드

- **내 휴가 정보**: 발생 총 n개 / 사용 n개 / 미사용 n개 / 결재 대기 n개(본인이 신청한 문서 중
  대기 상태)
- **내 결재 정보**: 결재 대기 문서 n개(본인이 결재자로 지정된 문서 중 대기 상태) / 처리 문서
  n개(본인이 승인·반려 완료한 문서)

## 9. 화면 구성 (GNB)

- 대시보드 (홈)
- 내 휴가정보 (연차 발생/사용 내역, 원장 상세 조회)
- 내 문서
  - 리스트: 내가 신청한 휴가계 목록 (상태별 필터)
  - 작성: 신규 휴가계 작성
- 결재함
  - 리스트: 내가 결재자로 지정된 문서 목록 (대기/처리완료 필터)
  - 상세보기: 개별 문서 승인/반려 처리
- 관리자 메뉴 (관리자 전용): 가입 승인, 프리랜서 정보 관리, 연차 수동 조정, 공휴일 관리

## 10. 기술 스택 (제안)

- Next.js (App Router) 풀스택 단일 배포
- Postgres DB — **Supabase**(Vercel Marketplace 연동)를 사용한다. Supabase는 DB 엔진과
  Realtime(7.1절 실시간 알림) 용도로만 사용하며, 인증은 Supabase Auth를 사용하지 않는다.
- ORM: Drizzle 또는 Prisma (구현 단계에서 확정) — Supabase Postgres에도 표준 Postgres 연결
  문자열로 동일하게 접속한다.
- 인증: 자체 이메일/비밀번호 (Auth.js Credentials 방식 등), 가입승인상태 체크를 로그인 게이트로
  사용. Supabase Auth와는 무관하게 독립적으로 동작한다.
- 실시간 알림: Supabase Realtime(Postgres Changes) — 전용 `Notification` 테이블만 구독
- UI: Tailwind CSS + shadcn/ui, datepicker 라이브러리 사용

세부 라이브러리·프로바이더 선택은 구현 계획 수립 및 실제 스캐폴딩 단계에서 확정한다.

**Supabase 채택 이유**: 애초 계획된 Postgres(Vercel Marketplace, 예: Neon)만으로는 실시간
알림(7.1절)을 구현하려면 별도의 pub/sub 인프라(예: Upstash Redis + SSE)를 직접 구축해야 한다.
Supabase는 Postgres Changes 기반 Realtime 구독을 표준 기능으로 제공하므로, 동일한 DB 벤더
안에서 이 요구사항을 해결할 수 있어 채택했다. 단, Realtime 구독은 브라우저가 Supabase에 직접
연결되는 구조이므로 Row Level Security(RLS) 정책 설계가 필요하며, 이를 단순화하기 위해 원본
테이블이 아닌 전용 `Notification` 테이블만 구독 대상으로 한정한다.

## 11. 에러 처리 / 엣지 케이스

- 잔여연차 부족 시 제출 차단
- 결재자 미지정 시 제출 차단
- 대기/승인 상태 문서와 기간이 겹치는 신규 신청 시 경고(비차단)
- 공휴일 미등록 구간은 주말만 제외하고 계산

## 12. 테스트 방향

- 연차 발생/소멸 배치 로직: 만근 판정(반차 예외 포함), 입사 1년 시점 소멸, 신규 사이클 반복
