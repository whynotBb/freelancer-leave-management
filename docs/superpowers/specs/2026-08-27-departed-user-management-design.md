# 퇴사자 관리 기능 Design

**Goal:** 프리랜서 정보 관리·결재담당자 관리 화면에서 대상자를 "퇴사" 처리할 수 있게 하고,
퇴사자를 모아 보는 전용 화면에서 복구하거나 정보를 영구 삭제할 수 있게 한다.

**Background:** 지금은 프리랜서·결재자를 시스템에서 내보내는 방법이 없다. 실제 퇴사가
발생하면 계정이 계속 활성 상태로 남아 로그인이 가능하고, 자동 연차 발생 배치도 계속
연차를 지급하며, 목록·콤보박스에도 계속 노출된다.

## 1. 범위

**포함**
- 프리랜서 정보 관리 / 결재담당자 관리 화면에 "퇴사" 액션 추가
- 신규 "퇴사자 관리" 화면 및 메뉴(최고관리자 전용)
- 퇴사자 복구, 정보 삭제(프리랜서: 완전 삭제 / 결재자: 익명화)
- 퇴사 처리 시 결재자의 대기 중인 결재 건을 처리 admin에게 위임하는 흐름

**제외**
- 퇴사 처리 이력을 별도 감사 로그 테이블로 남기는 것(복구 후 재퇴사 시 사유는 덮어써도 됨 — YAGNI)
- 결재자 대량 재배정 UI(위임은 "지금 이 최고관리자에게" 1건으로 충분, 개별 재배정은 기존
  기본 결재자 변경 기능으로 처리)
- 프리랜서 본인이 제출 중인 휴가 신청에 대한 특별 처리(퇴사 즉시 하위 데이터가 그대로 남고,
  이후 "정보 삭제" 시 함께 삭제된다 — 별도 차단 로직 불필요)

## 2. 데이터 모델

`users` 테이블에 컬럼 3개를 추가한다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `signup_status`(기존) | varchar | 새 값 `'RESIGNED'` 추가. 기존: PENDING / APPROVED / REJECTED |
| `resigned_at` | timestamp, nullable | 퇴사 처리 시각 |
| `resign_reason` | text, nullable | 퇴사 사유(필수 입력) |

**`RESIGNED`를 별도 status 값으로 두는 이유**: 이 코드베이스는 이미 프리랜서/결재자를
"활성 사용자"로 취급하는 모든 조회에서 `signupStatus === 'APPROVED'`를 필터로 쓰고 있다
(목록 조회, 자동 연차 발생 배치, 로그인 게이트). `RESIGNED`는 `APPROVED`가 아니므로 이
필터들이 **코드 수정 없이 퇴사자를 자동으로 제외**한다. 예외적으로 아래 지점들은 명시적으로
`RESIGNED` 여부를 확인하도록 손봐야 한다(4장 참조).

**복구(RESIGNED → APPROVED)** 시 `resigned_at`, `resign_reason`은 `null`로 되돌린다.

## 3. 정보 삭제 — 역할별로 동작이 다르다

**프리랜서: 완전 삭제.** 해당 사용자가 소유한 데이터를 전부 삭제한 뒤 `users` 행 자체를
삭제한다: `leave_grants`(userId), `leave_requests`(userId), `notifications`(recipientId),
`approver_changes`(userId), `attendance_exceptions`(userId), 마지막으로 `users` 행.
전부 "이 프리랜서 본인 소유" 데이터라 다른 사용자의 이력을 건드리지 않는다.

**결재자: 익명화(행은 유지).** 결재자의 `users.id`는 다른 사람들의 이력
(`leave_requests.approver_id`, `approver_changes.*`, `leave_grants.created_by`,
`attendance_exceptions.created_by`)에 참조되어 있다. 행을 진짜로 삭제하면 FK 제약
위반이거나, 억지로 cascade를 걸면 무관한 프리랜서의 휴가 이력까지 삭제된다. 대신:

- `name`을 `사용자#{id}(퇴사)` 형태로 덮어쓴다
- `email`을 `deleted-{id}@deleted.local`로 덮어쓴다(UNIQUE 제약 유지)
- `passwordHash`를 무효화한다(로그인 완전 차단)
- 이 결재자를 기본 결재자로 지정한 모든 프리랜서의 `defaultApproverId`를 `null`로 변경한다

이력 화면들은 `users.name`을 조인해서 보여주는 구조이므로, 위 처리만으로 승인 이력·발생
이력 등에 **기존 조회 코드를 건드리지 않고도** "사용자#12(퇴사)"가 자동으로 표시된다.

**두 경로 모두 되돌릴 수 없다.** 프리랜서는 데이터 자체가 사라지고, 결재자는 원본 개인정보가
사라져 복구할 데이터가 없다. 퇴사자 관리 화면의 삭제 확인 모달에 이 점을 명시한다.

## 4. 기존 로직과의 통합 지점

- **로그인 게이트**(`lib/auth/auth-options.ts`): 이미 `signupStatus !== 'APPROVED'`면
  로그인을 막는다. `RESIGNED`도 자동으로 막히지만, 에러 메시지("가입 승인 대기 중이거나
  거절된 계정입니다")가 부적절하므로 `RESIGNED`인 경우 "퇴사 처리된 계정입니다"로 분기한다.
- **자동 연차 발생 배치**(`lib/db/attendance-grant-batch.ts`): 후보 조회가
  `eq(users.signupStatus, 'APPROVED')` 기준이라 손댈 필요 없음.
- **기본 결재자 콤보박스**(`components/approver-combobox.tsx`가 소비하는
  `/api/admin/approvers`): 현재 결재자 전체를 반환한다 — `RESIGNED` 결재자를 제외하도록
  쿼리에 조건 추가 필요.
- **프리랜서/결재자 목록 조회**(`getApprovedFreelancers`, 결재담당자 관리 목록 API): 이미
  `signupStatus = 'APPROVED'` 필터라 손댈 필요 없음.

## 5. 화면 변경

### 5.1 프리랜서 정보 관리 / 결재담당자 관리

각 행에 "퇴사" 버튼 추가(최고관리자에게만 노출 — 결재자 계정은 이 버튼을 보지 못한다).
클릭 시 사유 입력 확인 모달:

- 확인 시 `RESIGNED` 처리 + `/admin/departures`로 이동
- **결재자 행이고, 대기(제출) 상태인 휴가 신청이 남아있는 경우**: 모달에 대기 건수를 표시하고
  기본 확인 버튼을 비활성화한다. 대신 **"나에게 위임하고 퇴사 처리"** 버튼을 제공 — 클릭 시
  대기 중인 `leave_requests.approver_id`를 전부 지금 로그인한 최고관리자 ID로 변경한 뒤
  같은 트랜잭션에서 퇴사 처리를 진행한다. 재배정된 각 신청의 신청인에게 "담당 결재자가
  변경되었습니다" 알림을 발송한다(기존 `APPROVER_CHANGED` 알림 타입 재사용).

### 5.2 퇴사자 관리(신규, 최고관리자 전용)

- 사이드바 "관리자 메뉴"에 추가(최고관리자에게만 노출)
- `RESIGNED` 상태 사용자 목록: 이름, 이메일, 역할(프리랜서/결재자), 퇴사일, 퇴사 사유
- 행별 액션:
  - **복구**: 확인 모달 → `APPROVED`로 되돌리고 `resigned_at`/`resign_reason` 초기화
  - **정보 삭제**: 확인 모달(되돌릴 수 없음을 명시) → 3장의 역할별 삭제/익명화 처리

## 6. 권한

퇴사 처리 / 복구 / 정보 삭제 전부 **최고관리자(SUPER_ADMIN) 전용**. 결재자(APPROVER)는
프리랜서 정보 수정 권한은 그대로 갖지만 이 기능들은 접근할 수 없다.

## 7. 에러 / 엣지 케이스

- 이미 `RESIGNED`인 사용자에게 "퇴사" 액션을 다시 시도 → 차단(그 사람은 이제 프리랜서 정보
  관리/결재담당자 관리 목록에 애초에 없으므로 UI상 발생하지 않음)
- 결재자 익명화 도중 이미 익명화된 이메일 패턴과 충돌 → `deleted-{id}@deleted.local`은
  `id`가 유일하므로 충돌 불가
- 최고관리자 본인을 퇴사 처리하려는 시도 → 이 화면들은 SUPER_ADMIN 대상이 아니므로 애초에
  버튼이 노출되지 않음(범위 밖)
